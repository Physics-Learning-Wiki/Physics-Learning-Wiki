## 降低贡献门槛与调动贡献积极性 — 设计文档

日期：2026-05-25
状态：待实施

---

## 背景与问题

Physics Learning Wiki（物理学习百科）面向全体物理爱好者，提供系统化物理学习平台，内容严重依赖社区贡献．当前处于冷启动阶段，几乎无外部贡献者．编辑组仅 2 人，无预算，站点运行在 GitHub Pages（考虑迁移 CloudFlare）．

### 核心问题

1. **贡献门槛过高**：需要 GitHub 账号、理解 Git/Markdown/LaTeX/PR 流程、手动维护 author 字段和 nav 配置
2. **无人知晓**：项目缺乏宣传，潜在贡献者根本不知道这个平台
3. **激励薄弱**：贡献者的署名存在但不够突出，缺少站点级认可机制

### 目标用户画像

主力贡献者：物理系本科生．知识正在形成中，有分享意愿但时间有限、技术背景参差不齐．

### 设计原则

- **零预算可落地**：所有方案基于免费服务（GitHub API、CloudFlare Workers 免费额度、GitHub Actions）
- **编辑组可控**：降低提交门槛的同时保留审核权，防止恶意内容
- **渐进式**：不推翻现有架构，在现有 MkDocs 静态站基础上增量添加能力
- **质量分级而非一刀切**：允许半成品存在但不误导读者

## 模块一：整体架构

### 现有架构

```
MkDocs 源码 (docs/*.md) → GitHub Actions 构建 → GitHub Pages 部署
贡献方式：GitHub PR 流程 / 邮箱投稿 → 编辑组手动整理
```

### 新增架构

```
┌────────────────────────────────────────────┐
│                  网站前端                     │
│  ┌──────────┐  ┌──────────┐  ┌───────────┐ │
│  │ MkDocs   │  │ 投稿页面  │  │ 社区角     │ │
│  │ 静态页面  │  │ (表单+    │  │ (展示已    │ │
│  │          │  │  编辑器)  │  │ 收录投稿)  │ │
│  └──────────┘  └────┬─────┘  └───────────┘ │
└─────────────────────┼───────────────────────┘
                      │ 提交
                      ▼
┌─────────────────────────────────────────────┐
│        CloudFlare Worker / Netlify Function  │
│      接收表单 → 格式化 → 创建 GitHub Issue     │
└─────────────────────┬───────────────────────┘
                      │ GitHub API
                      ▼
┌─────────────────────────────────────────────┐
│              GitHub 仓库                      │
│  ┌──────────┐  ┌──────────┐  ┌───────────┐ │
│  │ Issues   │  │  PR      │  │ Actions   │ │
│  │ (=投稿   │  │ (=传统   │  │ (=自动化  │ │
│  │  队列)   │  │  贡献)   │  │  流水线)  │ │
│  └──────────┘  └──────────┘  └───────────┘ │
└─────────────────────────────────────────────┘
```

### 关键设计决策

1. **GitHub Issues 作为投稿队列**：不引入新数据库．编辑组用熟悉的 Issue 界面审核．Issue 标签管理状态：
   - `投稿-待审核`：新提交的投稿
   - `投稿-已收录`：审核通过，已生成社区角页面
   - `投稿-需修改`：需要投稿者补充
   - `投稿-已拒绝`：不收录（附带原因）
   - `投稿-勘误`：页面错误修正
   - `投稿-建议`：非内容类的意见建议

2. **CloudFlare Worker 作为代理层**：
   - `POST /api/submit` → 验证 + 格式化 → 调用 GitHub Issues API 创建 Issue
   - 约 30 行代码，CloudFlare Workers 免费额度（10 万次/天）完全覆盖
   - 备选：如果暂不迁移 CloudFlare，可使用 Netlify Functions（项目已在用 Netlify 做 deploy preview）

3. **投稿页面是静态 HTML**：嵌入 MkDocs 站内（`docs/submit.md`），包含 Markdown 编辑器和表单

4. **社区角自动生成**：GitHub Actions 定期（每小时或每次 push）从 `投稿-已收录` 标签的 Issues 中提取内容，生成 `docs/community/` 下的 markdown 文件，随站点一起构建

### 不在范围内

- 用户注册/登录系统（利用 GitHub 账号体系，投稿者无需注册本站账号）
- 实时通知系统（利用 GitHub 的 Issue 通知机制）
- 投稿者与编辑组的站内私信（通过 Issue 评论沟通）

## 模块二：投稿表单设计

### 页面位置

- URL：`/submit/`（文件：`docs/submit.md`）
- 从导航栏可访问，编辑入口（edit-landing.md）增加指向此页的链接

### 表单结构

```
┌─────────────────────────────────────────┐
│         提交你的物理知识                  │
│                                         │
│  投稿类型：                              │
│  ○ 完整页面   ○ 笔记/提纲                │
│  ○ 勘误纠错   ○ 建议/想法                │
│                                         │
│  目标章节（选填）：                       │
│  [下拉选择：热学 > 第一定律 > ...]        │
│                                         │
│  标题：  [___________________]           │
│                                         │
│  正文：                                  │
│  ┌─────────────────────────────────┐    │
│  │  Markdown 编辑器（分栏实时预览）   │    │
│  │  工具栏：H1 H2 ** * $$ ` ```    │    │
│  │  快捷键插入：                   │    │
│  │    $$...$$ 行内公式              │    │
│  │    $$...$$ 块级公式              │    │
│  │    ??? note "标题"              │    │
│  │    ???+ warning "标题"          │    │
│  │                                 │    │
│  │  [编辑区]          │  [预览区]   │    │
│  │                    │            │    │
│  └─────────────────────────────────┘    │
│                                         │
│  署名方式：                              │
│  ○ 姓名/网名  ○ 匿名                    │
│  [_____________]                        │
│                                         │
│  联系方式（选填）：                       │
│  [_____________]                        │
│  （如需进一步沟通修改）                    │
│                                         │
│  [人机验证]  [提交]                      │
└─────────────────────────────────────────┘
```

### 设计细节

**投稿类型选择**：四种类型对应不同的正文 placeholder 提示：
- 完整页面：提示"请包含：问题引入 → 核心概念 → 公式推导 → 例题 → 易错点"
- 笔记/提纲：提示"半成品也没关系！把你的课堂笔记、复习提纲、思维导图粘贴进来即可"
- 勘误纠错：提示"请指出：具体章节 → 哪段文字/公式 → 错误描述 → 正确版本"
- 建议/想法：提示"对网站结构、内容方向、功能改进的任何想法都欢迎"

**Markdown 编辑器**：
- 分栏布局：左侧编辑、右侧实时渲染（含 LaTeX 公式渲染）
- 工具栏插入常用结构，降低 Markdown 学习成本
- 基于 CodeMirror 6 或 EasyMDE，前端纯静态实现
- 预览区使用 MathJax 渲染（与主站一致）

**目标章节下拉**：
- 从 `mkdocs.yml` 的 nav 结构自动生成层级下拉
- 选填，但编辑组处理时省去分类工作

**人机验证**：
- 使用 CloudFlare Turnstile（免费，无用户交互即可通过）
- 防止 Issue 垃圾提交

**提交后**：
- 前端显示"投稿已提交！编辑组将在 3-5 天内处理，如需跟进请保存此链接：[Issue URL]"
- 不要求投稿者注册，但提示：如果愿意注册 GitHub 账号并在 Issue 中参与讨论，修改会更高效

### 启动投稿页面的方式

- 从导航栏：新增"投稿"入口
- 从每页底部：在现有"在 GitHub 上编辑此页"旁边增加"快速投稿"链接
- 从 edit-landing.md：增加投稿表单作为第三条路径（现有：GitHub 编辑 + 邮箱投稿）

## 模块三：自动化流水线

### 3.1 LaTeX / 格式自动检查

**触发时机**：PR 提交、push 到 main

**检查项**（GitHub Actions workflow）：
- LaTeX 语法：`$$` 配对、常见错误（如 `\frac` 应在行间用 `\dfrac`）、未闭合的花括号
- Markdown 格式：空行规范、缩进、链接有效性
- 中文排版：中英文之间空格、标点规范（中文语境使用全角标点）
- 信息框规范：admonition 语法正确性

**失败时的行为**：
- 在 PR/Issue 下自动评论，指出具体文件和行号
- 提供修正建议（而非仅报错）
- 格式类问题标记为"建议修改"（非阻断），语法错误标记为"需修改"

**实现**：
- 扩展现有 `scripts/normalize_markdown_math.py`、`scripts/fix_inline_math_strict.py` 等
- 新增 `scripts/check-format.py`（中文排版、Markdown 规范检查）
- 新增 GitHub Actions workflow：`.github/workflows/check-content.yml`

### 3.2 Nav 自动生成

**问题**：新增页面需要手动编辑 `mkdocs.yml` 的 `nav` 部分，容易遗漏或出错

**方案**：
- 编写脚本 `scripts/generate-nav.py`，从 `docs/` 目录结构自动生成 nav 配置
- 规则：
  1. 每个目录下的 `index.md` 作为该章节的首页，其一级标题作为章节名
  2. 其他 `.md` 文件按文件名排序，标题从文件的一级标题提取
  3. `_` 开头的目录（如 `_static`）和特殊文件（`edit-landing.md`、`CNAME`）自动排除
  4. 生成的 nav YAML 注入到 `mkdocs.yml` 的 `nav` 段
- 在 `hooks/on_env.py` 或构建前脚本中自动执行
- 手动排序需求：在各目录中放置 `_order.txt` 文件，一行一个文件名，指定该目录的文件顺序

**注意**：需要保留 `mkdocs.yml` 中非 nav 的其他配置不变

### 3.3 Author 自动提取

**问题**：目前 `page.meta.author` 需要手动维护在文件 frontmatter 中，容易遗漏

**方案**：
- 在构建前通过脚本从 git 历史自动提取每页的贡献者
- 流程：
  1. `git log --follow --format='%an|%ae' -- <file>` 获取所有修改过该文件的作者
  2. 去重、计数（按 commit 次数或修改行数排序）
  3. 将结果写入该文件的 frontmatter `author` 字段（或构建时注入页面上下文）
- 通过 Issue 投稿被编辑组整理为正式页面的：编辑者在 commit message 中使用 `Co-authored-by: 投稿者名 <email>` 以保留原始贡献者归属
- 注意不要覆盖已有的手动指定的 author（以手动为优先）

**实现**：
- 新脚本：`scripts/update-authors.py`
- 在 CI build workflow 中作为 pre-build 步骤运行
- 或在 `hooks/on_env.py` 中作为构建时 hook 动态注入

### 3.4 投稿内容基础筛选

**触发时机**：新的投稿 Issue 创建时（通过 GitHub Actions `issues` 事件）

**检查项**（非阻断，仅自动标记）：
- 字数检查：正文字数 < 20 → 自动评论"投稿内容过短，请补充更多细节"
- 垃圾检测：包含常见 spam 关键词 → 自动打标签 `spam` 并关闭
- 格式完整性：缺少标题或正文 → 自动评论提示补充

**实现**：
- `.github/workflows/triage-submission.yml`

## 模块四：内容质量分级

### 三级定义

| 级别 | 标识 | 含义 | 展示位置 | 进入条件 |
|------|------|------|---------|---------|
| 🌱 社区投稿 | `community` | 来自投稿入口，未经深度审核 | 社区角专区 | Issue 被编辑组打上"已收录"标签 |
| ✏️ 审校中 | `review` | 编辑组已介入整理，仍需补充 | 主站对应章节 | 编辑组整理后发布到 docs 目录 |
| ✅ 稳定版 | `stable` | 内容完整，经至少一位编辑审阅 | 主站对应章节 | 编辑组成员审阅通过并签字 |

### 视觉呈现

**社区投稿页面**：
- 在"社区角"分区展示（`/community/` 路径下）
- 页面上方显示醒目横幅：
  > ⚠️ 本文来自社区投稿，内容未经 Physics Learning Wiki 团队审核，仅供交流参考．如发现错误，欢迎在下方评论区指出或提交勘误．

**审校中页面**：
- 在页面底部状态栏显示（在现有 footer 区域上方新增一行）：
  > 🔧 本页面状态：审校中 · 以下部分待完善：[列表] · 欢迎参与讨论

**稳定版页面**：
- 无额外标记．仅在页面底部状态栏显示：
  > ✅ 稳定版

### 实现方式

1. **社区角**：
   - GitHub Actions 从 `投稿-已收录` Issue 提取正文和元数据
   - 生成 `docs/community/<issue-number>.md`，自动填入 frontmatter：
     ```yaml
     ---
     status: community
     author: <投稿者署名>
     source_issue: <issue-url>
     submission_date: <投稿日期>
     ---
     ```
   - 社区角首页 `docs/community/index.md` 自动聚合展示卡片列表

2. **审校中 / 稳定版**：
   - 在文件 frontmatter 中指定：
     ```yaml
     ---
     status: review  # 或 stable
     reviewer: <审核者ID>
     review_date: <审阅日期>
     ---
     ```
   - 修改 `partials/comments.html` 模板，在现有 footer 内容上方根据 `page.meta.status` 渲染对应状态栏
   - 稳定版页面如有新 commit（内容修改），CI 自动将 status 降级为 `review`

### 交互流程

```
社区提交 → 编辑组审核 → 打标签"已收录"
  ├─ → Actions 自动生成 /community/ 页面（status: community）
  └─ → 编辑组整理→发布到正式目录→改为 status: review
        └─ → 编辑审阅通过→改为 status: review
              └─ → 有新修改→自动回退到 status: review
```

## 模块五：社区运营与激励

### 5.1 站点级贡献者墙

**新增页面**：[贡献者](docs/intro/contributors.md)

**内容**：
- 按贡献量排序的所有贡献者列表（头像 + 署名 + 贡献页面数）
- 本月活跃贡献者
- 投稿贡献者与 GitHub 贡献者合并展示
- 每年/每学期的"贡献之星"归档

**数据来源**：
- GitHub 贡献者：`git log --all --format='%an|%ae' | sort | uniq -c | sort -rn`
- 投稿贡献者：从 Issue 标签 `投稿-已收录` 中提取署名信息

**刷新频率**：每月由 GitHub Actions 自动更新

### 5.2 社区渠道建设

**初期（冷启动阶段）**：
- 建立 QQ 群或微信群（一个主群即可，不必过早细分）
- 群内发布：当前最需要的内容清单、写作指南、优秀投稿示例

**B站宣传**：
- 物理教学视频涨粉 → 视频简介/评论区引导到 Wiki
- "如何贡献"系列短视频（3 分钟以内，一集只讲一个操作）
- 精选社区投稿制作"本周最佳投稿"视频

### 5.3 章节维护人制度

- 每个学科模块（力学/热学/电磁学/光学/近代物理）招募 1-2 名维护人
- 职责：关注本章 Issue、引导投稿方向、初审投稿
- 在章节首页展示维护人信息
- 维护人本身从活跃贡献者中产生——鼓励贡献者通过深度参与成为维护人
- 初期由现有编辑组成员兼任，逐步移交

### 5.4 内容冲刺活动

- 定期在社区发起主题冲刺，如"两周补完电学部分"
- 在 QQ 群 / Issue 中发布任务认领表
- 冲刺结束后在贡献者墙特别鸣谢
- 一种低成本但有效的集中贡献方式，也适合与高校物理社团合作

## 实施优先级

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **P0** | 模块一 + 模块二（投稿门户 + 后端） | 直接拆掉最大壁垒：不需要 GitHub 账号 |
| **P1** | 模块三（自动化流水线） | 低成本减少编辑组摩擦，顺便做了 |
| **P1** | 模块四（内容质量分级） | 为半成品提供容身之所，让投稿系统闭环 |
| **P2** | 模块五（社区运营） | 需要前面模块落地、有内容基础后才有效果 |

### 建议分两期实施

**第一期**：模块一 + 模块二 + 模块三 → 投稿门户上线，自动化到位
**第二期**：模块四 + 模块五 → 社区角和内容分级上线，开始运营推广

## 技术选型汇总

| 组件 | 技术选型 | 理由 |
|------|---------|------|
| 后端代理 | CloudFlare Workers（备选 Netlify Functions） | 免费额度足够，零运维 |
| 投稿队列 | GitHub Issues | 无需新数据库，编辑组用惯 GitHub |
| Markdown 编辑器 | EasyMDE 或 CodeMirror 6 | 轻量，纯前端，支持实时预览 |
| 人机验证 | CloudFlare Turnstile | 免费，无用户交互 |
| LaTeX 预览 | MathJax（与主站一致） | 已有配置，无需额外引入 |
| 自动化 | GitHub Actions | 已有 CI 基础，零成本 |
| 社区角生成 | GitHub Actions + Python 脚本 | 静态生成，无需后端 |

## 未涉及但值得未来探索的方向

- **章节评论/行级批注**：类似 Hypothesis 的行级注释系统，可让读者在具体段落下讨论
- **内容翻译系统**：为多语言版本做准备
- **习题互动系统**：嵌入可交互的物理模拟和在线判题
- **AI 辅助审稿**：使用 LLM 对投稿进行初步质量评估和格式标准化
- **移动端 App**：原生移动应用，降低手机用户的浏览和贡献门槛
